## Summary

Allow active validators to **opt in** to specific external chains they want to support, replacing the current all-or-nothing model. Per-chain income is tracked and distributed only to supporting validators, while protocol-level allocations (dev fund, reserve emission) remain global.

### Key changes

- **NodeAccount.SupportedChains**: New field allowing validators to declare which chains they support. Empty = all chains (backwards compatible, no migration needed).
- **MsgAddNodeChainSupport / MsgRemoveNodeChainSupport**: Two new message types for validators to manage their chain preferences, with activation deferred to the next churn.
- **Chain-aware keygen partitioning**: At churn, eligible nodes are partitioned by their supported chains set. Each viable partition gets its own keygen/vault.
- **Per-chain reward bucketing**: Swap fees, outbound fees, and network fees are attributed to the originating chain. Distribution is pro-rata by effective bond across each chain's vault members.
- **Chain-aware consensus**: Observation, network fee, solvency, and errata handlers use chain-scoped 2/3 supermajority (active + retiring vault members for the chain).
- **Chain-aware slashing**: Non-signer penalties forfeit the offender's share of chain income rather than slashing bond.
- **Liquidity cap**: When chain support drops below 2/3 of active validators, new inflows are capped at ChainLiquidityRunePerValidator x validatorsForChain.
- **Auto-ragnarok**: Chains with fewer than MinimumNodesForBFT supporters automatically ragnarok at churn. Affected vault members cannot unbond until drain completes.
- **Bifrost integration**: Chain clients gain SetShouldObserveCallback to pause/resume observation based on vault membership.
- **API additions**: supported_chains on node account, supporting_validators/liquidity_cap_applied on inbound addresses.
- **Prometheus metrics**: thornode_chain_supporting_validators and thornode_chain_liquidity_cap_headroom_ratio gauges.

### New Mimir keys

| Key                            | Default   | Purpose                                      |
| ------------------------------ | --------- | -------------------------------------------- |
| MinNodeChainSupport            | 1         | Min chains a node must support               |
| ChainLiquidityRunePerValidator | 100k RUNE | Per-validator cap when less than 2/3 support |
| MinimumNodesForBFT             | 4         | Min nodes for viable chain group             |
| ChainSubBFTRatioNum/Denom      | 2/3       | Ratio below which cap activates              |

### Regression tests

- opt-in-chain-security/happy-path: opt-in, churn, chain-only vault, swap, rewards
- opt-in-chain-security/liquidity-cap: sub-2/3 support, cap enforcement
- opt-in-chain-security/chain-ragnarok: sub-MinimumNodesForBFT, auto-ragnarok
