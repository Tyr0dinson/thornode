# THORNode v4.0.0: Cosmos SDK v0.54.4

This is a coordinated, state-breaking upgrade candidate, not authorization to activate it. No activation height is assigned. Complete the rehearsal and distributed validation gates below before release or mainnet use.

## Baseline and exact target

Work began from clean commit `757199a809e069932aeaff1628a6483d5fdde416`, with SDK v0.53.0, CometBFT v0.38.21, Wasmd v0.54.0 and wasmvm/v2 v2.2.1. The previously described SDK v0.53.8/Comet v0.38.23 and `/v4` module transition were **not** in this checkout. No existing uncommitted changes were overwritten. The Go module remains `gitlab.com/thorchain/thornode/v3`; release metadata and the upgrade handler are `4.0.0`. A Go module path change is not required for this SDK migration.

Official GitHub releases were rechecked September 10, 2026. The selected latest stable v0.54 patch is **v0.54.4**; neither v0.55 nor an SDK prerelease is selected.

The [Cosmos release-family lifecycle](https://docs.cosmos.network/sdk/latest/release-family) lists SDK v0.53 and v0.55 in active families, excluding v0.54. Its [maintenance policy](https://github.com/cosmos/security/blob/main/POLICY.md) limits maintenance and compatibility support to active families. This target is deliberate; successful local compatibility checks do **not** establish guaranteed ongoing maintenance for v0.54.

## Dependency decisions

Wasmd v0.70.3 declares SDK v0.54.0 and wasmvm/v3 v3.0.7; SDK v0.54.4 declares CometBFT v0.39.4. The full application was checked beyond the earlier Wasmd exported-package resolution probe.

EVM v1.0.0-rc2 already broke baseline `go list -m all` with `github.com/cosmos/evm/evmd@v0.0.0: unknown revision evmd/v0.0.0`. Against SDK v0.54, its dependency-test closure also requested removed `x/group` through IBC v10. Upstream EVM v0.6.3 preserves the old signing conversion and resolves the invalid evmd reference. All EVM v0.7.x candidates changed EIP712 preimages for existing THORChain direct messages; fixed pre-upgrade signature tests caught this, so v0.7.x was rejected. The lower-looking version is intentional. The five signing/codec packages used by THORNode are retained unchanged in `third_party/cosmos-evm`, with upstream license and provenance.

The root and `test/simulation` module graphs pass `go mod tidy`; `third_party/cosmos-evm` is consumed only through a root `replace` and is not tidied as a standalone module. The local EVM module excludes the unused EVM application and its incompatible IBC v10 dependency-test closure. Fixed pre-upgrade signing fixtures and the application suite pass with the retained packages. Remove this compatibility module when upstream supports THORChain custom Amino encoding and those fixtures pass unchanged.

All existing root replacements remain, including op-geth, Viper v1.17 (app overrides), the LevelDB query/store pin, keyring, btcd and Binance codec/crypto replacements. The simulation module retains its Ledger THORChain replacement and now explicitly shares the root keyring/Viper/LevelDB replacements, which Go does not inherit through a required module. The simulation Ledger replacement has a baseline `-tags ledger` API mismatch; see validation results.

CometBFT compiles its modern libp2p dependency even when that transport is disabled. This raised shared multiaddr/CID versions and broke Bifrost's standalone `go-libp2p-core` imports. Required Bifrost changes use upstream `go-libp2p/core`, modern discovery/DHT APIs and matching Mplex. Peer key bytes, peer IDs, protocol IDs, rendezvous and address ordering remain unchanged. Explicit TCP/WebSocket transports, Noise/TLS security order and Yamux/Mplex selection preserve the previous configured protocol choices. Resource management and other library defaults still require load and mixed-version threshold-signing validation.

## Execution, signing and contracts

- Execution remains sequential. No BlockSTM runner or bank object store is enabled. Comet retains legacy networking, flood mempool and disabled AdaptiveSync; no application-side Comet mempool mode is enabled.
- SDK v0.54 disables block gas metering by default. THORNode explicitly calls `SetDisableBlockGasMeter(false)`. The existing THORNode infinite transaction gas decorator and injected-transaction ante bypass remain.
- Bank runs first in end-block, followed by the existing module order. Bifrost injections remain first in proposals. SDK now counts protobuf transaction envelopes itself, so the old extra envelope reservation is removed; final aggregate byte checks remain. This can admit more ordinary transactions at the same byte limit without changing their order.
- Store and Log imports move to v2; tx/upgrade imports move under the SDK. Log context calls retain filtering and consensus-failure termination. Store tracing was removed upstream; the local constructor keeps an unused writer argument for caller compatibility.
- Direct, direct-aux, textual and THORChain custom Amino remain configured. Ethereum and multisig registration remain. No new key types or consensus authority are enabled. Fixed HEAD-baseline fixtures verify the exact old EIP712 preimages and signatures for THORChain Send and Deposit across network prefixes. Physical Ledger validation is a separate gate.
- Existing Wasmd query allowlist, query context marker, custom message routing, permissions, bank wrapper and scheduled execution remain. Pinned-code initialization reads committed state after loading and repopulates the VM cache.
- New Wasmd separate pin/unpin gas charges stay zero to retain the prior behavior. Other configured register constants match the old tag. The existing `CompileCost * 100` field is unused by both Wasmd tags; actual compilation charges come from the VM, so contract gas must be measured rather than inferred from that field.
- Wasmd adds `ibc2_port_id` metadata when instantiating/migrating a contract even though THORNode does not register an IBC module. The exported consensus schema also includes an empty authority object; no authority address is configured. These metadata additions, and new account-number allocation, explain the measured Wasm state-fixture differences.
- Native packaging now copies the wasmvm/v3 v3.0.7 Linux libraries for the build architecture. Contract VM changes are consensus relevant even when storage schemas do not change.

## State migration

Registered modules are genutil, auth, bank, upgrade, params, consensus, thorchain, wasm, denom and scheduler. Staking/mint keepers and stores exist but their modules are not in ModuleManager. No reference-app gov/epochs/IBC/group migrations were added.

| Module                    | Source consensus-version change | Required behavior                                                                                                                                 |
| ------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| auth                      | 5 → 6                           | Remove global account-number counter; retain existing account numbers, sequences and public keys. New account-number allocation changes upstream. |
| wasm                      | 4 → 4                           | No migration for state already at 4. Older maps run the registered 1→2→3→4 paths.                                                                 |
| bank / consensus / params | 4 / 1 / 1 unchanged             | Retain stores and run module-manager version selection.                                                                                           |

`CustomWasmModule.RegisterServices` now registers only upstream migrations, not upstream message/query servers. The legacy Wasm parameter subspace has the tagged migration key table needed by migration 2→3. Tests execute the actual module manager from Wasm versions 1, 2 and 3 and verify access conversion and code identity; they also execute auth 5→6.

The standard upgrade handler retains active-validator-version updates **before** `RunMigrations`. Release `4.0.0` registers this handler. No store additions, deletions or renames are justified by the selected registered modules; the params store remains. If actual chain-state analysis reveals a store change, create a dedicated `app/upgrades/<semver>` package as required by `app/upgrades/standard/upgrades.go`.

The legacy SDK47 consensus-parameter fallback uses a writable cache branch and writes only after migration succeeds. It does not reset existing InitChain/ProcessProposal/finalize state with `NewNextBlockContext`. Pinned initialization uses `NewContext(true)` for reads. Test-only raw store contexts now use cache branches too.

Source module versions are not evidence of the actual mainnet version map. Never stamp a missing version to bypass migration errors. Export/query the old binary's module-version map and retain it with rehearsal evidence.

## Rehearsal and activation gates

No recent mainnet database was supplied. The local default node directory contains only a small, old database and is not a recent-mainnet rehearsal source. No production database or signing state was modified.

1. Obtain a recent mainnet snapshot and exact old binary/image, recording snapshot height/hash, chain ID, binary digest, module versions and wasm cache contents. Work on an isolated copy with test validator keys and no public peers; never reuse an active validator's signing key/state in a connected clone.
2. Inventory balances and total supply per denom; pools; vault membership and funds; bonds; pending outbounds; contract code hashes, storage, admins and pinned IDs; account numbers/sequences/keys; validator identities and powers. Save normalized old-binary query/export results.
3. Rehearse an old-binary halt for the exact `4.0.0` plan at an isolated test height. Start the upgraded binary on the copied database without skip-upgrade flags, export/reset shortcuts or manually changing the module-version map. Retain logs proving validator-version updates and each selected migration completed.
4. Verify the inventory after startup and after representative transactions/contract calls. Explain only intended differences: software/active-validator versions, auth migration's removed global counter and new allocation, selected older Wasm parameter migrations, native VM gas results and fuller proposal byte utilization. Any unexplained balances/supply/pools/vaults/bonds/outbounds/identity/sequence difference blocks activation.
5. Run multiple validators through the same upgrade, compare app hashes at every height, restart each, test a lagging node's catch-up and restore via state sync including pinned contracts. Repeat mixed old/new Bifrost DHT, party formation and complete threshold signing under load. A two-host transport handshake is not this test.
6. Validate physical Ledger and Ethereum wallet signing against the upgraded binary. Review v0.54 support ownership, release identity, complete build artifacts and outstanding validation failures. Only a separate authorized release process may choose an activation height.

See [validation and independent review results](sdk-v054-validation.md) for reproducible commands and the distinction between dependency resolution, application checks and mainnet readiness.
